03
01 / FRICTION

장애 대응은 어디에서 시간을 잃는가

데이터가 없어서 느린 게 아니다. 세 개의 도구에 나뉘어 있고, 그 사이를 사람이 손으로 잇기 때문에 느리다.

STEP 01

알람 수신

임계치 초과 통보. 무엇이 넘었는지는 알지만 왜 넘었는지는 없다.

STEP 02

대시보드 확인

Grafana에서 시간축을 알람 시점으로 맞추고 관련 패널을 찾는다.

STEP 03

메트릭 파고들기

PromQL을 직접 쓴다. 메트릭명·라벨을 기억하거나 찾아야 한다.

STEP 04

로그 대조

Kibana로 옮겨 같은 구간을 다시 지정하고 쿼리를 다시 쓴다.

STEP 05

상관관계 판단

메트릭과 로그를 머릿속에서 겹쳐 가설을 세운다. 전적으로 사람 몫.

공통 원인
도구를 옮길 때마다 시간축 · 대상 · 필터를 손으로 다시 맞춘다.

03~05번은 담당자의 숙련도에 전적으로 의존한다. 같은 장애라도 누가 보느냐에 따라 도달 시간이 갈린다. 자동화되지 않은 것은 수집이나 시각화가 아니라 수집된 것을 읽는 절차다.

이 문서는 근거 없는 수치를 싣지 않는다. "평균 몇 분이 걸린다"는 baseline은 아직 측정되지 않았고, Phase 1의 측정 항목으로 남겨둔다 → 05 측정

기존 도구는 어디까지 해주는가

다섯 축으로 비교했다. 앞의 세 축은 이미 성숙했고, 뒤의 두 축에서 전부 비어 있다.

도구 수집 · 저장 시각화 · 탐색 임계치 알람 도구 간 상관 원인 후보 제시
Prometheus 메트릭 시계열 PromQL 수동 작성 규칙 기반 없음 없음
Grafana 저장소 연결만 대시보드 · 패널 규칙 · 알림 채널 나란히 배치까지 없음
Elasticsearch · Kibana 로그 색인 Query DSL 수동 작성 임계치 워처 없음 없음
observe‑copilot 직접 저장하지 않음

01 / OPPORTUNITY

우리가 노리는 빈칸

관측성 파이프라인을 다섯 단계로 끊어 보면, 마지막 두 칸에서만 사람이 여전히 전부를 한다.

해결됨

수집

익스포터·에이전트로 자동화됐다

해결됨

시각화

대시보드는 충분히 성숙했다

해결됨

알람

임계치 규칙으로 감지된다

빈칸

상관

메트릭과 로그를 겹쳐 보는 일은 사람 몫이다

빈칸

해석

무엇부터 볼지 좁혀주는 단계. 아무도 하지 않는다

THESIS
보여주는 것 다음 단계는 좁혀주는 것이다.

LLM은 정확히 이 빈칸을 메우는 기술이다. 다만 대신 결론을 내리는 방식이 아니라, 흩어진 근거를 한 화면에 모아 후보에 순위를 붙이는 방식으로만 쓴다.

왜 지금인가

컨텍스트 길이가 시계열 구간과 로그 수백 줄을 한 번에 담을 만큼 커졌고, 툴 콜링으로 "쿼리 생성 → 검증 → 실행"을 분리할 수 있게 됐다. 생성과 실행 사이에 검증을 끼울 수 없었다면 이 설계는 성립하지 않는다.

왜 이 도메인인가

정답이 데이터에 있다. 요약에 쓰인 수치는 전부 수집된 원본에 존재해야 하므로, 환각을 사후 검증 가능한 형태로 통제할 수 있다. 근거를 붙일 수 없는 도메인이었다면 안전장치를 만들 방법이 없다.

02 / TARGET

문제 정의와 타겟 사용자

B2C가 아니다. 이미 관측 스택을 운영 중인 사람이 쓰는 내부 도구다.

서비스 운영자

알람을 받고 가장 먼저 대응하는 사람. 대시보드를 세 개 열어 시간축을 맞추는 동안 장애는 계속 진행된다. 필요한 것은 새 대시보드가 아니라 어디부터 볼지에 대한 후보다.

백엔드 개발자

PromQL·Query DSL을 매일 쓰지는 않는다. 메트릭명과 라벨을 매번 찾는 데 시간을 쓴다. 자연어로 묻고 변환된 쿼리를 확인할 수 있으면 그 시간이 사라진다.

전제

이미 스택은 있다

Prometheus·Elasticsearch·Grafana가 이미 돌고 있다는 것이 전제다. 이 도구는 저장소를 대체하지 않고 그 위에 얹힌다. 도입 비용이 "읽기 권한 하나"에 그치는 것이 설계 목표다.

범위 밖

1인 · 소규모 운영 전제

멀티테넌시와 세분화된 권한 관리는 넣지 않는다. 이 결정으로 인증·격리 설계를 통째로 덜어내고, 그 시간을 요약 품질 검증에 쓴다.

KEY INSIGHT
이 도구의 출력은 답이 아니라 검토 순서다.

최종 판단은 항상 사람이 한다. 그래서 요약의 품질보다 근거에 도달하는 속도가 더 중요한 지표다. 요약이 틀려도 근거가 옆에 있으면 사용자는 손해를 보지 않는다.

08
02 / SCOPE

MVP 범위

못 하는 것이 아니라 의도적으로 미룬 것. 제외 항목에는 전부 근거가 붙는다.

포함 — IN SCOPE
  • 자연어 → 메트릭 질의
    의도를 파싱해 PromQL로 변환하고 Prometheus를 조회해 결과를 요약한다
  • 자연어 → 로그 질의
    Elasticsearch 로그를 검색하고 결과를 요약한다
  • 알람 시 자동 근본원인 요약
    임계치 초과 시 관련 메트릭·로그를 자동 수집해 원인 후보를 텍스트로 제시한다
  • 요약과 원본의 동시 노출
    대시보드가 LLM 요약과 원본 데이터(그래프·로그 라인)를 나란히 표시한다
제외 — OUT OF SCOPE
  • 자동 조치 — 재시작·스케일링·설정 변경
    오판 시 리스크가 회수 불가능하다. 1차 버전에서 절대 넣지 않는다
  • 초 단위 실시간 대응
    매 신호마다 LLM을 호출하면 비용과 지연이 선형으로 늘어난다. 수 분 단위 배치로 축소
  • 멀티테넌시 · 세분화 권한
    1인·소규모 운영 전제. 인증 설계를 덜어내고 요약 품질 검증에 시간을 쓴다
  • 모델 파인튜닝
    프롬프트 설계와 쿼리 검증 범위 안에서 해결한다
제외 항목 중 자동 조치만 성격이 다르다. 나머지 셋은 "나중에 한다"이지만, 자동 조치는 이 도구의 정체성상 영구 제외다. 읽기 전용이라는 사실이 시스템 컨텍스트 · 권한 설계 · 실패 모드 전부의 전제가 되기 때문이다.

02 / GUARDRAILS

LLM 출력 안전장치 4건

원칙을 구호로 적으면 위반 여부를 판정할 수 없다. 각 항목에 "무엇이 위반인가"를 붙여 코드 리뷰 기준으로 쓴다.

G-1  근거 병기 강제

요약을 단독으로 반환하는 경로를 만들지 않는다

응답 DTO는 요약과 근거(원본 로그 라인, 메트릭 시계열)를 항상 함께 담는다.

위반 판정 — 근거 필드 없이 요약만 있는 응답 타입이 존재하면 설계 위반. 프런트에서 근거를 감추는 것도 위반.

G-2  가설로 표현

확정형으로 서술하지 않는다

원인 후보는 가설형 문장으로 쓰고 확신도(높음/중간/낮음)를 함께 반환한다.

위반 판정 — "원인은 X입니다" 형태의 출력, 또는 확신도 필드가 비어 있는 응답.

G-3  자동 조치 금지

시스템 상태를 바꾸는 동작을 구현하지 않는다

재시작·스케일링·설정 변경 없음. 이 도구는 읽기 전용이다.

위반 판정 — 외부 시스템으로 나가는 쓰기 호출이 하나라도 존재하면 위반. 연결 자체를 읽기 전용 계정으로 제한한다.

G-4  배치 주기 요약

초 단위 실시간 대응을 시도하지 않는다

알람 대응은 수 분 단위 배치로 처리한다. 비용과 지연을 예측 가능한 범위에 묶는다.

위반 판정 — 알람 수신 경로에서 동기 LLM 호출이 일어나면 위반.

왜 판정 기준까지 적는가
"근거를 함께 보여줄 것"은 판정 불가, "근거 없이 요약만 있는 응답은 설계 위반"은 판정 가능하다.

안전장치는 배경 설명이 아니라 코드 리뷰 기준이다. 리뷰에서 통과/불통과를 가를 수 없는 문장은 지켜지지 않는다.

02 / VOICE

확신도와 표현 규칙

출력의 문장 구조 자체가 안전장치다. 사실 → 동시성 → 가설 → 확신도 → 근거 순서를 고정한다.

이렇게 말한다

"14:02부터 5xx 비율이 3.1%로 올랐습니다. 같은 시각 DB 커넥션 대기 시간도 함께 증가했습니다. 커넥션 풀 고갈이 원인일 가능성이 있습니다 — 확신도 중간. 다만 같은 시각 배포 이력도 있어 배제하지 않았습니다 — 확신도 낮음."

근거 · 메트릭 2건 · 로그 18줄  → 아래 첨부

이렇게 말하지 않는다

"DB 커넥션 풀 고갈이 원인입니다. 풀 크기를 40으로 늘리세요."

확정형 · 조치 지시 · 근거 없음 — 세 가지 모두 위반

확신도 · 높음

근거가 시간과 대상 모두에서 일치하고, 알려진 실패 패턴과 부합한다.

확신도 · 중간

시간대는 일치하나 인과를 특정할 근거가 부족하다. 동시 발생과 인과를 구분해 서술한다.

확신도 · 낮음

정황만 있다. 배제하지 않기 위해 남긴다 — 목록에서 지우는 것도 판단이기 때문이다.

원칙: 관측된 사실을 먼저 말하고 판단은 사용자에게 남긴다. 조치를 지시하지 않는다.
확신도 3단계는 기획서에서 확정된 항목이다. 각 단계의 판정 정의는 이 문서의 제안이며 Phase 3 채점 결과로 조정한다.

성공 기준과 리스크 대응

성공 기준은 전부 측정 가능한 형태로 적는다. 아직 목표값을 정할 수 없는 항목은 "미정"이라고 쓴다.

리스크와 대응

환각 — 근거 없는 원인 제시

원본 인용 강제 · 가설 표현 강제 · 확신도 명시. 요약 내 수치가 원본에 없으면 경고 플래그.

비용 · 지연

실시간 대신 수 분 단위 배치. 동일 질의 패턴 캐싱을 전제로 설계한다.

데이터 부족 — 실제 이상 신호가 없다

부하로 정상 패턴을 만들고 장애를 주입한다 → 04 검증 전략

03 / LAYERS

레이어 구성

각 레이어가 무엇을 하지 않는지까지 적어야 경계가 지켜진다.

데이터 소스

Prometheus Elasticsearch Kafka  메트릭 · 로그 · 이벤트 원천. 이 도구가 소유하지 않는다.

수집 · 정규화

Spring Boot  원천 데이터를 LLM 입력용 컨텍스트로 가공한다. 토큰 예산 안으로 축약하는 책임도 여기.

배치 · 스케줄링

Spring Batch Quartz  주기적 집계, 이상탐지 룰 트리거. 알람 대응이 동기 경로를 타지 않게 막는 지점.

LLM 오케스트레이션

Claude API  자연어 파싱 → 쿼리 변환 → 결과 요약. 인터페이스 뒤에 둔다.

저장

PostgreSQL  질의 이력, 집계 결과, 요약 로그. 이 도구가 쓰기를 하는 유일한 대상이다.

API · 시각화 · 배포

REST Grafana EKS  요약과 근거를 함께 반환하는 응답 계약, 대시보드 연동, 컨테이너 배포.

CORE RULE
LLM은 인터페이스 뒤에 있다.

도메인 로직에 Claude API 호출을 직접 박지 않는다. 근거는 두 가지다.

01  기획서에 EXAONE 병행 가능성이 열려 있다.

02  더 중요하게는, LLM 없이 테스트할 수 없는 코드는 수치 측정이 불가능하다. 측정을 요구하는 이 프로젝트에서 DIP는 취향이 아니라 전제다.

쓰기가 나가는 곳은 하나뿐

PostgreSQL. 외부 관측 스택 어디에도 쓰지 않는다.

03 / CODE BOUNDARIES

코드 레이어 책임 경계

의존 방향은 단방향이다. 역방향 참조는 금지한다.

레이어책임하지 말 것그렇게 정한 이유
ControllerHTTP 요청/응답, 입력 검증, DTO 변환비즈니스 로직, Repository 직접 호출HTTP 계약이 도메인 규칙을 침범하면 테스트가 서블릿에 묶인다
Service비즈니스 로직, 트랜잭션 경계HTTP · 서블릿 타입 의존요약 로직은 HTTP 없이 단위 테스트할 수 있어야 측정이 성립한다
Repository영속성 접근비즈니스 판단저장 방식 교체가 도메인 규칙 변경으로 번지지 않게
Entity도메인 상태API 응답으로 직접 노출지연 로딩·순환 참조 문제, 그리고 내부 스키마가 API 계약에 묶인다
명명 규칙

이름만 보고 역할을 알 수 있어야 한다

레이어 접미사를 강제한다 — ~Controller · ~Service · ~Repository · ~Request / ~Response

금지 — Util · Manager · Helper · Common. 아무 내용도 담지 않는 이름은 무엇이든 담게 된다.

중복 처리 기준

두 번째 쓸 때 공통화한다

동시에 반대 방향 제약도 둔다 — 우연히 모양만 같은 코드는 합치지 않는다. 바뀌는 이유가 다르면 남겨둔다.

중복 제거를 무조건 밀면 바뀌는 이유가 다른 코드가 한 덩어리로 묶여 나중에 더 큰 비용이 된다.

패키지 물리 배치(도메인별 vs 계층별)는 미결이다. 첫 도메인 코드를 쓰는 시점에 정하고 기록한다 — 추측으로 채우지 않는다.

알람이 입력이고 요약이 출력이다. 그 사이 어디에서도 시스템 상태를 바꾸지 않는다.

지연은 결함이 아니라 선택이다

알람과 요약 사이에 수 분의 간격이 있다. 초 단위로 당기면 호출 비용과 지연이 선형으로 늘고, 알람 폭주 시 요약이 오히려 늦어진다. 주기값은 조정 예정 — 실측 후 확정한다.

정규화가 이 흐름의 실제 난도다

메트릭과 로그는 시간 해상도도 형식도 다르다. 둘을 하나의 시간축에 정렬하고 토큰 예산 안으로 줄이면서 신호를 버리지 않는 것이 요약 품질을 좌우한다. LLM 프롬프트보다 여기가 먼저다.

03 / FAILURE MODES

실패 모드와 복구 전략

외부 의존이 다섯 개인 시스템에서는 정상 경로보다 실패 경로 설계가 품질을 결정한다.

Prometheus 조회 실패

로그만으로 응답한다

메트릭 근거가 없다는 사실을 응답에 명시한다. 부분 실패를 감춘 요약은 금지 — 사용자가 근거의 완전성을 오인한다.

Elasticsearch 다운

메트릭만으로 응답한다

같은 원칙. 확신도는 자동으로 한 단계 낮춘다 — 근거가 절반이면 확신도 산정도 절반이어야 한다.

LLM 타임아웃 · 한도 초과

요약 없이 원본만 반환한다

도구는 조회 도구로 강등되지만 죽지 않는다. 수집된 데이터는 이미 확보돼 있으므로 재수집 없이 재요약만 시도한다.

잘못된 쿼리 변환

실행 전 검증에서 차단

검증 실패 시 실행하지 않고 변환 결과를 그대로 노출한 뒤 재질의를 유도한다. 틀린 쿼리를 조용히 실행하는 것이 최악이다.

Kafka 컨슈머 지연

다음 주기로 이월

배치 주기 내에 도착하지 못한 이벤트는 다음 주기에 포함한다. 처리 지연을 지표로 계측한다.

환각 수치

수집 데이터와 대조

요약에 등장한 숫자가 수집된 원본에 존재하지 않으면 경고 플래그를 붙인다. 근거 병기 구조가 이 검사를 가능하게 만든다.

공통 원칙
외부 시스템 하나가 죽어도 나머지 기능은 동작한다. 그리고 무엇이 빠졌는지 응답에 적는다.

두 번째 문장이 없으면 첫 번째 문장은 위험해진다. 반쪽 근거로 만든 요약을 온전한 것처럼 내보내는 순간, 이 도구는 안전장치가 없는 도구가 된다.

구조 결정  D‑01 ~ 04

SOLID를 나열하는 대신, 이 프로젝트에서 실제로 걸리는 지점만 남겼다.

D-014계층으로 분리하고 의존 방향을 단방향으로 고정한다확정 각 레이어의 "하지 말 것"을 함께 명시해야 경계가 지켜진다. 나열만으로는 위반을 판정할 수 없다. (+) 요약 로직을 HTTP 없이 단위 테스트할 수 있다  (−) DTO 변환 코드가 늘어난다 — 측정 가능성과 맞바꾼 값
D-02Entity를 API 응답으로 직접 노출하지 않는다확정 그대로 직렬화하면 지연 로딩·순환 참조 문제가 생기고, 내부 스키마가 API 계약에 묶인다. (+) 스키마 변경이 API 파괴로 번지지 않는다  (−) 매핑 계층 유지 비용
D-03LLM · 데이터 소스는 인터페이스 뒤에 둔다 DIP확정 Claude API 호출을 도메인 로직에 직접 박지 않는다. 기획서에 EXAONE 병행 가능성이 있고, 무엇보다 LLM 없이 테스트할 수 없는 코드는 수치 측정이 불가능하다. (+) 모델 교체 가능 · LLM 없이 도메인 테스트 가능  (−) 추상화 한 겹  — 이 프로젝트는 측정이 목적이므로 비용을 감수한다
D-04프롬프트 구성 / API 호출 / 응답 파싱을 한 클래스에 몰지 않는다 SRP확정 셋은 바뀌는 이유가 각각 다르다 — 프롬프트는 품질 실험으로, 호출은 SDK·모델 변경으로, 파싱은 응답 스키마 변경으로 바뀐다. (+) 프롬프트 문구를 바꿔가며 측정할 때 나머지를 건드리지 않는다  (−) 클래스 수 증가
LSP · ISP는 넣지 않았다. 현재 상속 구조도 비대한 인터페이스도 없어 걸릴 지점이 없다. 억지로 채우면 판정 불가능한 구호가 된다.

03 / DECISIONS · 2

안전장치 결정  D‑05 ~ 09

네 건은 기획서에서 확정된 제약이고, 하나(D‑08)는 리스크 표에서 도출한 것이다.

D-05LLM 요약을 근거 없이 반환하는 경로를 만들지 않는다확정 사용자가 요약을 사실로 오인하는 것이 이 도구의 최대 리스크다. 구조로 막지 않으면 문구로 막을 수 없다. 판정 — 근거 필드 없는 응답 타입의 존재 자체가 위반. 응답 DTO 설계 시점에 강제된다.
D-06원인 후보는 가설형 + 확신도(높음/중간/낮음)로 표현한다조정 예정 3단계는 확정. 각 단계의 판정 정의는 제안 상태이며 채점 결과를 보고 조정한다. 재검토 조건 — "중간"이 전체의 대부분을 차지하면 단계 구분이 정보를 주지 못하는 것이므로 기준을 다시 나눈다.
D-07자동 조치를 구현하지 않는다 — 이 도구는 읽기 전용이다확정 오판 시 리스크가 회수 불가능하다. 이 결정은 "나중에 한다"가 아니라 영구 제외다. (+) 권한 · 실패 모드 · 감사 설계가 통째로 단순해진다  (−) "알아서 고쳐주는" 데모 임팩트를 포기
D-08변환된 쿼리는 검증 후 실행하고, 사용자에게 노출한다확정 기획서에 직접 쓰인 문장은 아니고 리스크 표(환각)에서 도출했다. 자연어→쿼리 변환은 틀릴 수 있고, 틀린 쿼리의 결과는 그럴듯한 그래프로 나타나 발견되지 않는다. 검증 항목 — 문법 · 메트릭/필드 존재 여부 · 기간 범위. 실패 시 실행하지 않고 변환 결과를 노출한다.
D-09알람 대응은 수 분 단위 배치로 처리한다조정 예정 실시간 대응은 비용·지연 문제로 제외. 다만 주기값은 미정이다 — 실측 없이 정하면 근거 없는 숫자가 된다. 확정 조건 — 요약 응답 시간과 호출당 비용을 측정한 뒤 결정한다 → 05 측정

04 / DATA

실제 이상 신호를 어떻게 만드는가

가장 큰 제약은 기술이 아니라 데이터다. 정상 트래픽도 장애 트래픽도 존재하지 않는 상태에서 시작한다.

STEP 01

부하 생성 — 정상 패턴 축적

k6 Locust 인위적 트래픽을 발생시켜 평상시 메트릭 분포를 만든다.

순서가 중요하다. 정상 패턴이 없으면 "이상"을 정의할 기준선이 없다. 부하 생성이 장애 주입보다 반드시 먼저다.

STEP 02

장애 주입 — 이상 신호 생성

예외 발생, 응답 지연 삽입, DB 커넥션 풀 고갈 등을 코드 레벨에서 재현한다.

주입한 원인을 우리가 알고 있다는 점이 핵심이다. 이것이 곧 채점용 정답 라벨이 된다.

부수 효과
이 과정 자체가 포트폴리오의 근거 자료가 된다.

"실제 장애 없이 어떻게 검증했는가"는 면접에서 반드시 나오는 질문이다. 장애 주입 시나리오와 그 결과 채점표가 답변이 된다. 검증 수단을 만드는 일이 검증 결과만큼 보여줄 것이 있다.

주의 — 주입한 장애는 실제 장애보다 깨끗하다. 신호가 명확하고 노이즈가 적다. 여기서 얻은 적중률은 상한값으로 읽어야 하며, 그대로 실환경 성능이라고 주장하지 않는다.

04 / SCENARIOS

장애 시나리오 카탈로그

각 시나리오는 주입 방법 · 나타나야 할 신호 · 정답을 함께 정의한다. 정답이 없으면 채점할 수 없다.

ID시나리오주입 방법나타나야 할 신호정답 라벨
S-1DB 커넥션 풀 고갈 풀 크기를 줄이고 동시 요청 수를 올린다 응답시간 p95 급증 · 커넥션 획득 대기 증가 · 로그에 pool timeout 반복 커넥션 풀
S-2외부 의존 지연 전파 호출하는 외부 API 응답에 인위적 지연을 삽입한다 해당 의존을 쓰는 엔드포인트만 지연 · 스레드 점유 증가 · 다른 경로는 정상 외부 의존
S-3예외 급증 (5xx) 특정 경로에 예외를 주입한다 5xx 비율 급증 · 동일 스택트레이스가 로그에 반복 · 특정 경로에 집중 코드 결함 · 배포
S-4메모리 압박 해제되지 않는 참조를 만들어 힙 점유를 늘린다 GC 시간 증가 · 응답시간이 톱니 형태로 반복 상승 · 특정 경로에 국한되지 않음 메모리

왜 네 개인가

기획서 성공 기준은 "2~3개 이상"이다. 넷으로 잡은 이유는 혼동 쌍을 만들기 위해서다 — S-1과 S-2는 둘 다 지연으로 나타나고, S-3과 S-4는 둘 다 오류율을 올린다. 구분하지 못하면 그 사실이 측정된다.

채점 방식

요약이 제시한 후보 목록에 정답 라벨이 포함됐는지, 몇 번째 순위였는지, 확신도가 적절했는지를 함께 본다. 정답을 1순위로 맞히는 것과 후보에 넣기라도 하는 것은 다른 성과이므로 나눠 기록한다.

05 / BLOCKER

선결 과제 — 무엇을 '성공'으로 볼 것인가

1순위 지표인 변환 성공률을 재려면, 재는 자를 먼저 만들어야 한다. 기획서에도 "수동 평가 기준 마련 필요"로 남아 있는 항목이다.

등급 A

완전 일치

실행 결과가 정답 쿼리와 동일하다.

등급 B

의미 일치

표현은 다르지만 같은 결론에 도달한다. 예 — rate() 윈도가 허용 범위 안에서 다름.

등급 C

부분 실패

메트릭명은 맞으나 필터 · 기간 · 집계 함수가 틀렸다. 사용자가 쿼리를 보면 고칠 수 있는 수준.

등급 D

실패

실행 불가이거나 전혀 다른 대상을 조회한다.

먼저 만들어야 하는 것
정답 쌍이 붙은 질의 세트.

자연어 질의와 그에 대응하는 정답 쿼리를 짝지어 고정해야 한다. 이 세트가 없으면 첫 baseline 측정 자체가 성립하지 않고, 이후 프롬프트를 바꿨을 때 개선을 주장할 근거가 없다.

왜 등급을 넷으로 나누는가

성공/실패 2분법은 C를 D로 만든다. 실제로는 C가 가장 많이 나올 구간이고, 개선 여지가 어디 있는지도 C의 비율이 알려준다.

이 등급표의 상태

제안 첫 채점을 해보고 조정한다. 등급 정의도 측정 대상이다.

기획서 원문: "자연어 질의 → 정확한 쿼리 변환 성공률 (수동 평가 기준 마련 필요)" — 이 문서가 그 기준의 초안이다
